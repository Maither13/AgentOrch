## 交付摘要

**背景与目标**：为上游服务提供可复用的基础加法能力，替代各业务方重复实现。成功标准是合法输入返回正确和、非法输入返回结构化 4xx 而非 5xx，且 pytest 套件覆盖全部 P0 验收标准并可一键执行。

**功能列表（7 条）**
- P0：F1 `POST /add` 加法接口、F2 参数校验与结构化错误码、F3 负数/零/小数支持、F4 pytest 单元测试套件
- P1：F5 `GET /health` 健康检查
- P2：F6 批量加法、F7 非有限结果错误码

**接口定义**：`POST /add`，请求 `a`/`b`（number，必填，拒绝字符串数字与布尔值），响应 `result`/`a`/`b`；错误码 `INVALID_ARGUMENT`(400)、`INVALID_JSON`(400)、`UNSUPPORTED_MEDIA_TYPE`(415)、`RESULT_NOT_FINITE`(422)。另含 `/health` 与 `/add/batch` 定义。

**数据字段**：4 个实体（AddRequest / AddResponse / ErrorResponse / HealthResponse），含类型、约束、默认值；服务无状态、不持久化。

**验收标准（19 条）**：AC1–AC15 覆盖全部 P0 功能，每条均为可自动化断言的具体条件（如 AC5 明确断言 `0.1+0.2` 严格等于 `0.30000000000000004`，AC9 明确布尔值必须被拒，AC14 要求 `pytest` 退出码为 0 且用例数 ≥12）。AC16–AC19 对应 P1/P2。

**待确认问题（3 条，按影响排序）**
1. HTTP 方法与路径未在需求中指定——我按 REST 定为 `POST /add` + JSON body；若调用方期望 `GET /add?a=1&b=2` 或带版本前缀，接口契约与测试用例都要改。
2. 浮点精度策略——AC5 现按 IEEE 754 双精度严格断言；若涉及金额需改定点数或舍入，会影响 `result` 取值及全部相关 AC。
3. F6/F7（P2）是否纳入本迭代——若不实现，AC17–AC19 需移出验收范围。

需要提醒的一点：需求原文只说「一个 /add 接口 + pytest 测试」，我额外定义了 `/health`（P1）和批量接口（P2）作为可选扩展，并显式标注了优先级与对应 AC，便于你按排期裁剪——若希望严格收敛到最小范围，可直接删除 F5–F7 及 AC16–AC19，不影响 P0 部分的完整性。
